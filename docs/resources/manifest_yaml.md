# kubernetes_manifest_yaml

Applies a single Kubernetes object from raw YAML using Server-Side Apply (SSA). Unlike `kubernetes_manifest`, it does not require the typed OpenAPI schema at plan time. See RFC-011.

`kubernetes_manifest_yaml` is a schemaless alternative to [`kubernetes_manifest`](manifest.md). It takes raw YAML for exactly one object and applies it with [Server-Side Apply](https://kubernetes.io/docs/reference/using-api/server-side-apply/) (SSA). Because it does not build a typed schema from the cluster's OpenAPI document at plan time, it works well for CRDs and for migrating configurations from community `kubectl_manifest` resources.

Drift is tracked only for the fields this resource's [field manager](https://kubernetes.io/docs/reference/using-api/server-side-apply/#field-management) owns (projected from `managedFields`), so server defaults and fields owned by other controllers do not produce spurious diffs.

~> **Note** This resource manages a **single** object. To apply a multi-document YAML file, use `for_each` over [`provider::kubernetes::manifest_decode_multi(...)`](../functions/manifest_decode_multi.md) and apply CRDs before the custom resources that use them.

~> **Note** `yaml_body` is marked **sensitive** because a manifest may contain a `Secret`. Terraform will not display its contents in plan output.

## Schema

### Required

- `yaml_body` (String, Sensitive) Raw YAML for exactly one Kubernetes object. Marked sensitive because the manifest may contain a Secret.

### Optional

- `delete` (Block, Optional) Deletion options. (see [below for nested schema](#nestedblock--delete))
- `field_manager` (String) Server-Side Apply field manager name. Use a unique value when sharing an object with other managers.
- `force_conflicts` (Boolean) Force apply, taking ownership of fields managed by another field manager.
- `force_replace_on` (List of String) Dotted field paths (e.g. "spec.volumeClaimTemplates", "spec.serviceName") that force replacement of the object when their value changes, instead of an in-place update. Use this for Kubernetes-immutable fields (e.g. a StatefulSet's `volumeClaimTemplates`, `serviceName`, `selector`, `podManagementPolicy`) that would otherwise be rejected on apply. Combine with `delete { propagation_policy = "Orphan" }` to keep the underlying Pods/PVCs across the replacement (the recreated object re-adopts them).
- `ignore_fields` (List of String) Dotted field paths (e.g. "spec.replicas") to exclude from the owned-field projection, so an external controller (e.g. an HPA) can own them without causing drift.
- `timeouts` (Block, Optional) (see [below for nested schema](#nestedblock--timeouts))

## Example Usage

```terraform
resource "kubernetes_manifest_yaml" "example" {
  yaml_body = <<-YAML
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: nginx
      namespace: default
    spec:
      replicas: 2
      selector:
        matchLabels:
          app: nginx
      template:
        metadata:
          labels:
            app: nginx
        spec:
          containers:
            - name: nginx
              image: nginx:1.27
  YAML

  # Block until the rollout completes; surface pod errors (CrashLoop/ImagePull) on failure.
  wait {
    rollout = true
    timeout = "5m"
  }
}
```

### Replacing a StatefulSet on an immutable-field change (orphan upgrade)

Some fields (a StatefulSet's `volumeClaimTemplates`, `serviceName`, `selector`, `podManagementPolicy`, and similar) cannot be updated in place. List those paths in `force_replace_on` so Terraform replaces the object instead of attempting a rejected update. Combine it with `delete { propagation_policy = "Orphan" }` to keep the underlying Pods and PVCs; the recreated object re-adopts them.

```terraform
# StatefulSets have immutable fields (volumeClaimTemplates, serviceName, selector,
# podManagementPolicy). Changing them requires deleting and recreating the object.
# `force_replace_on` turns such a change into a replacement, and
# `delete { propagation_policy = "Orphan" }` keeps the Pods/PVCs so the recreated
# StatefulSet re-adopts them (an in-place "upgrade" that preserves data).
resource "kubernetes_manifest_yaml" "database" {
  yaml_body = <<-YAML
    apiVersion: apps/v1
    kind: StatefulSet
    metadata:
      name: database
      namespace: default
    spec:
      serviceName: database
      replicas: 3
      selector:
        matchLabels:
          app: database
      template:
        metadata:
          labels:
            app: database
        spec:
          containers:
            - name: db
              image: postgres:16
      volumeClaimTemplates:
        - metadata:
            name: data
          spec:
            accessModes: ["ReadWriteOnce"]
            resources:
              requests:
                storage: 10Gi
  YAML

  force_replace_on = [
    "spec.volumeClaimTemplates",
    "spec.serviceName",
    "spec.selector",
    "spec.podManagementPolicy",
  ]

  delete {
    propagation_policy = "Orphan"
  }

  wait {
    rollout = true
    timeout = "10m"
  }
}
```

## Import

Import an existing object using a `key=value` identifier:

```shell
terraform import kubernetes_manifest_yaml.example 'apiVersion=apps/v1,kind=Deployment,namespace=default,name=nginx'
```

Because `yaml_body` is required and cannot be reconstructed from the live object, add matching configuration after importing (or use `terraform plan -generate-config-out`).
