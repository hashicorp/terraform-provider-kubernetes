# kubernetes_ingress_v1

Ingress is a collection of rules that allow inbound connections to reach the endpoints defined by a backend. An Ingress can be configured to give services externally-reachable urls, load balance traffic, terminate SSL, offer name based virtual hosting etc.

- `host` (String) host is the fully qualified domain name of a network host, as defined by RFC 3986. Note the following deviations from the "host" part of the URI as defined in RFC 3986: 1. IPs are not allowed. Currently an IngressRuleValue can only apply to
   the IP in the Spec of the parent Ingress.
2. The `:` delimiter is not respected because ports are not allowed.
	  Currently the port of an Ingress is implicitly :80 for http and
	  :443 for https.
Both these may change in the future. Incoming requests are matched against the host before the IngressRuleValue. If the host is unspecified, the Ingress routes all traffic based on the specified IngressRuleValue.

host can be "precise" which is a domain name without the terminating dot of a network host (e.g. "foo.bar.com") or "wildcard", which is a domain name prefixed with a single wildcard label (e.g. "*.foo.com"). The wildcard character '*' must appear by itself as the first DNS label and matches only a single label. You cannot have a wildcard label by itself (e.g. Host == "*"). Requests will be matched against the Host field in the following way: 1. If host is precise, the request matches this rule if the http host header is equal to Host. 2. If host is a wildcard, then the request matches this rule if the http host header is to equal to the suffix (removing the first label) of the wildcard rule.

## Example Usage

```terraform
resource "kubernetes_ingress_v1" "example_ingress" {
  metadata {
    name = "example-ingress"
  }

  spec {
    default_backend = {
      service = {
        name = "myapp-1"
        port = { number = 8080 }
      }
    }

    rule {
      http = {
        path = [
          {
            path = "/app1/*"
            backend = {
              service = {
                name = "myapp-1"
                port = { number = 8080 }
              }
            }
          },
          {
            path = "/app2/*"
            backend = {
              service = {
                name = "myapp-2"
                port = { number = 8080 }
              }
            }
          },
        ]
      }
    }

    tls {
      secret_name = "tls-secret"
    }
  }
}

resource "kubernetes_service_v1" "example" {
  metadata {
    name = "myapp-1"
  }
  spec {
    selector = {
      app = kubernetes_pod_v1.example.metadata.0.labels.app
    }
    session_affinity = "ClientIP"
    port {
      port        = 8080
      target_port = 80
    }

    type = "NodePort"
  }
}

  metadata {
    name = "myapp-2"
  }
```

## Example using Nginx ingress controller

```terraform
resource "kubernetes_service_v1" "example" {
  metadata {
    name = "ingress-service"
  }
  spec {
    port {
      port        = 80
      target_port = 80
      protocol    = "TCP"
    }
    type = "NodePort"
  }
}

resource "kubernetes_ingress_v1" "example" {
  wait_for_load_balancer = true
  metadata {
    name = "example"
  }
  spec {
    ingress_class_name = "nginx"
    rule {
      http = {
        path = [{
          path = "/*"
          backend = {
            service = {
              name = kubernetes_service_v1.example.metadata.0.name
              port = {
                number = 80
              }
            }
          }
        }]
      }
    }
  }
}
```

## Migration to Plugin Framework

`kubernetes_ingress_v1` is implemented using the Terraform Plugin Framework. Apply the object syntax changes below before upgrading. The resource type and Kubernetes object identity are retained.

### Object configuration and state upgrade

The resource now uses state schema version 1 and upgrades existing version 0
state automatically. Identity schema version 1 is unchanged. Existing
`kubernetes_ingress_v1` resources need no `moved` block or re-import.

Keep `metadata`, `spec`, `rule`, `tls`, and `timeouts` as blocks. Change these
single objects to `name = { ... }` arguments:

- `spec[0].default_backend`, and its `resource`, `service`, and `service.port`.
- `spec[0].rule[*].http`, and every `http.path[*].backend` with its `resource`,
  `service`, and `service.port`.

The repeated paths inside `http` now use a list of objects, `path = [{ ... }]`.
Keep all path elements and their order. For example, replace the released
`http { path { backend { service { ... } } } }` nesting with:

```terraform
rule {
  http = {
    path = [{
      path      = "/app"
      path_type = "Prefix"
      backend = {
        service = {
          name = "app"
          port = { number = 80 }
        }
      }
    }]
  }
}
```

In references and lifecycle paths, remove indexes only for converted objects.
For example, `spec[0].rule[0].http[0].path[0].backend[0].service[0].port[0].number`
becomes `spec[0].rule[0].http.path[0].backend.service.port.number`.
An `ignore_changes` entry uses this same new path. Keep the `spec`, `rule`, and
`path` indexes because those values still contain lists.

Replace dynamic singleton blocks with conditional objects. For example:

```terraform
default_backend = var.enable_default_backend ? {
  service = { name = "app", port = { number = 80 } }
} : null
```

Module input types must use `object(...)` for these fields and `list(object(...))`
for `http.path`. For a service backend, an optional input can be declared as:

```terraform
variable "default_backend" {
  type = object({
    service = optional(object({
      name = string
      port = object({ number = optional(number), name = optional(string) })
    }))
  })
  default = null
}
```

Terraform JSON configuration uses objects for these fields, for example
`"default_backend": {"service": {"name": "app", "port": {"number": 80}}}`.
The `http.path` value remains an array. Omitted optional objects stay omitted
or `null`; do not add empty objects or new backends merely to change syntax.
The converter preserves configured ports and backend alternatives and rejects
historical singleton lists containing more than one element.

Before upgrading, confirm that the current configuration has an empty plan. Review the plan after upgrading; do not apply unexpected replacement or specification changes.

`wait_for_load_balancer` remains optional. When omitted, its state value remains `null` and creation does not wait for a load balancer endpoint; set it to `true` to enable that wait.

There is one narrow compatibility exception: if `metadata.labels = {}` or `metadata.annotations = {}` was explicitly configured but stored as `null` by the previous provider, the first upgrade plan can show an in-place update from `null` to `{}` for those maps. This update changes Terraform state only: it must not write to the Kubernetes API or replace the object, and the next plan must be empty. This exception does not cover omitted metadata arguments, selectors, TLS hosts, or other configuration changes.

The deprecated `kubernetes_ingress` resource remains on SDKv2 and uses the incompatible v1beta1 ingress schema. A cross-type `moved` block from `kubernetes_ingress` to `kubernetes_ingress_v1` is not supported. The `kubernetes_ingress_v1` data source remains on SDKv2.

### Resource identity

With Terraform 1.12 or later, resource identity contains `api_version` (`networking.k8s.io/v1`), `kind` (`Ingress`), `name`, and `namespace`. The existing namespace/name import identifier is unchanged.

## Import

```
terraform import kubernetes_ingress_v1.<TERRAFORM_RESOURCE_NAME> <KUBE_NAMESPACE>/<KUBE_INGRESS_NAME>
```
