Data Sources — Deep Dive & Migration Guide

terraform-provider-kubernetes · SDKv2 → Plugin Framework

1. What Is a Data Source?

A data source is a read-only construct in Terraform. It lets a configuration look up information that already exists — either in the target infrastructure or anywhere an API can describe — and expose that information as attributes that other parts of the configuration can reference.

Unlike a resource, a data source:

  • Never creates, modifies, or deletes anything in the API.
  • Has no lifecycle beyond reading (no Create, Update, or Delete methods).
  • Runs during terraform plan (and again during apply if the value is needed) rather than only during apply.
  • Is tracked in state only for caching — the state is refreshed every run.
Kubernetes examples in this provider: kubernetes_namespace_v1, kubernetes_secret_v1, kubernetes_server_version, kubernetes_nodes, kubernetes_pod_v1, and ~20 others — all living under kubernetes/data_source_kubernetes_*.go.

2. Using a Data Source in a Terraform Config File

Yes — data sources are referenced directly in .tf configuration files. The HCL keyword is data, not resource.

# Declare the data source
data "kubernetes_namespace_v1" "staging" {
  metadata {
    name = "staging"
  }
}

# Reference its attributes elsewhere in the same config
resource "kubernetes_config_map_v1" "app_config" {
  metadata {
    namespace = data.kubernetes_namespace_v1.staging.metadata[0].name
    name      = "app-config"
  }
  data = {
    env = "staging"
  }
}

The reference syntax is always data.<type>.<local_name>.<attribute>. You cannot reference a data source as if it were a resource (no kubernetes_namespace_v1.staging — that would look for a managed resource).

Timing: Terraform evaluates data sources during the plan phase when all their inputs are known. If an input depends on a resource that hasn't been created yet, Terraform defers the read to the apply phase.

3. How a Data Source Works — End-to-End Flow

Here is the full lifecycle of a data source call from HCL config to state:

1
Parse & validate
Terraform parses the data block and validates every attribute against the schema the provider declared for that data source (required fields present, correct types, etc.).
2
Provider configure
Before any reads happen, the provider's Configure method runs once, establishing the Kubernetes client (KubeClientsets). This client is passed into every data source read via meta (SDKv2) or req.ProviderData (Framework).
3
Read / Refresh
The data source's Read function executes. It calls the Kubernetes API (e.g., conn.CoreV1().Namespaces().Get(…)), maps the response to schema attributes, and writes the result into state.
4
State stored & attributes exposed
Terraform stores the read values under a synthetic ID (set via d.SetId(…) in SDKv2 or resp.State.Set(…) in Framework). Downstream resources can now reference those attribute values.
5
Every subsequent plan
The data source is re-read on every terraform plan / terraform apply. There is no "drift detection" — the current API value is always authoritative.

4. Anatomy of a Data Source in SDKv2 (Current State)

All data sources in this provider today live in the kubernetes/ package and are written with terraform-plugin-sdk/v2. Two components define each one:

4a. The schema function

Returns a *schema.Resource — the same struct used for managed resources, but without Create/Update/Delete hooks.

SDKv2 · kubernetes/data_source_kubernetes_namespace_v1.go
func dataSourceKubernetesNamespaceV1(deprecationMessage string) *schema.Resource {
    return &schema.Resource{
        Description:        "Query a namespace within a Kubernetes cluster.",
        ReadContext:        dataSourceKubernetesNamespaceV1Read,
        DeprecationMessage: deprecationMessage,

        Schema: map[string]*schema.Schema{
            "metadata": metadataSchema("namespace", false),
            "spec": {
                Type:     schema.TypeList,
                Computed: true,
                Elem: &schema.Resource{
                    Schema: map[string]*schema.Schema{
                        "finalizers": {
                            Type:     schema.TypeList,
                            Optional: true,
                            Elem:     &schema.Schema{Type: schema.TypeString},
                        },
                    },
                },
            },
        },
    }
}

4b. The Read function

Called by Terraform during plan/apply. It receives the config state via *schema.ResourceData, calls the API, and writes results back.

SDKv2 · kubernetes/data_source_kubernetes_namespace_v1.go
func dataSourceKubernetesNamespaceV1Read(
    ctx context.Context, d *schema.ResourceData, meta interface{},
) diag.Diagnostics {
    conn, err := meta.(KubeClientsets).MainClientset()
    if err != nil {
        return diag.FromErr(err)
    }

    metadata := expandMetadata(d.Get("metadata").([]interface{}))
    d.SetId(metadata.Name)

    namespace, err := conn.CoreV1().Namespaces().Get(ctx, metadata.Name, metav1.GetOptions{})
    if err != nil {
        return diag.FromErr(err)
    }

    d.Set("metadata", flattenMetadataFields(namespace.ObjectMeta))
    d.Set("spec", flattenNamespaceV1Spec(&namespace.Spec))
    return nil
}

4c. Provider registration

The data source is wired into the provider via DataSourcesMap in kubernetes/provider.go:

SDKv2 · kubernetes/provider.go
DataSourcesMap: map[string]*schema.Resource{
    "kubernetes_namespace":    dataSourceKubernetesNamespaceV1("Deprecated; use kubernetes_namespace_v1."),
    "kubernetes_namespace_v1": dataSourceKubernetesNamespaceV1(""),
    "kubernetes_secret_v1":    dataSourceKubernetesSecretV1(""),
    "kubernetes_server_version": dataSourceKubernetesServerVersion(),
    // ... 20+ more
},

5. SDKv2 vs. Plugin Framework — Key Differences

Concern SDKv2 Plugin Framework
Type *schema.Resource struct implementing datasource.DataSource
Registration DataSourcesMap on schema.Provider slice returned by provider.DataSources()
Schema map[string]*schema.Schema datasource/schema.Schema with typed Attribute structs
Read signature func(ctx, *schema.ResourceData, interface{}) diag.Diagnostics func(ctx, datasource.ReadRequest, *datasource.ReadResponse)
State writes d.Set("key", value) + d.SetId(…) resp.State.Set(ctx, &model) (typed Go struct)
Client access meta.(KubeClientsets) req.ProviderData via Configure()
Type name Map key string in DataSourcesMap resp.TypeName in Metadata() method
Errors diag.FromErr(err) resp.Diagnostics.AddError(summary, detail)

6. Migrating a Data Source — Step-by-Step

The following steps walk through converting an existing SDKv2 data source (e.g., kubernetes_namespace_v1) to the Plugin Framework. The Framework provider lives in internal/framework/provider/. See schedulingv1/priority_class_v1.go as a reference for how a migrated resource is structured — a data source follows the same pattern but only needs Metadata, Schema, and Read.

Step 1 — Create the package directory

Follow the existing convention: one directory per Kubernetes API group.

internal/framework/provider/corev1/
    namespace_v1.go          # struct + Metadata + Configure + Schema + Read
    namespace_v1_model.go    # Go state model struct
    namespace_v1_schema.go   # schema definition (optional split)

Step 2 — Define the state model

Replace the loosely-typed schema.ResourceData map with a concrete Go struct that mirrors the schema. Every attribute becomes a typed types.* field.

Framework · namespace_v1_model.go
package corev1

import "github.com/hashicorp/terraform-plugin-framework/types"

type NamespaceV1Model struct {
    ID       types.String        `tfsdk:"id"`
    Metadata []MetadataModel     `tfsdk:"metadata"`
    Spec     []NamespaceSpecModel `tfsdk:"spec"`
}

type NamespaceSpecModel struct {
    Finalizers []types.String `tfsdk:"finalizers"`
}

Step 3 — Define the Schema

Use datasource/schema (not resource/schema). Data source attributes are almost always Computed: true (they come from the API), with only the lookup key (e.g., metadata.name) being Required: true.

Framework · namespace_v1_schema.go
package corev1

import (
    "context"
    "github.com/hashicorp/terraform-plugin-framework/datasource"
    dschema "github.com/hashicorp/terraform-plugin-framework/datasource/schema"
    "github.com/hashicorp/terraform-plugin-framework/types"
)

func (d *NamespaceV1DataSource) Schema(
    _ context.Context, _ datasource.SchemaRequest, resp *datasource.SchemaResponse,
) {
    resp.Schema = dschema.Schema{
        MarkdownDescription: "Query attributes of a Kubernetes namespace.",
        Attributes: map[string]dschema.Attribute{
            "id": dschema.StringAttribute{Computed: true},
        },
        Blocks: map[string]dschema.Block{
            "metadata": dschema.ListNestedBlock{
                NestedObject: dschema.NestedBlockObject{
                    Attributes: map[string]dschema.Attribute{
                        "name": dschema.StringAttribute{Required: true},
                        "uid":  dschema.StringAttribute{Computed: true},
                        "labels": dschema.MapAttribute{
                            ElementType: types.StringType,
                            Computed:    true,
                        },
                    },
                },
            },
            "spec": dschema.ListNestedBlock{
                NestedObject: dschema.NestedBlockObject{
                    Attributes: map[string]dschema.Attribute{
                        "finalizers": dschema.ListAttribute{
                            ElementType: types.StringType,
                            Computed:    true,
                        },
                    },
                },
            },
        },
    }
}

Step 4 — Implement the struct and required methods

Framework · namespace_v1.go
package corev1

import (
    "context"
    "github.com/hashicorp/terraform-plugin-framework/datasource"
    "github.com/hashicorp/terraform-provider-kubernetes/kubernetes"
    metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
)

// Compile-time interface checks
var _ datasource.DataSource          = (*NamespaceV1DataSource)(nil)
var _ datasource.DataSourceWithConfigure = (*NamespaceV1DataSource)(nil)

type NamespaceV1DataSource struct {
    SDKv2Meta func() any
}

func NewNamespaceV1DataSource() datasource.DataSource {
    return &NamespaceV1DataSource{}
}

// Metadata sets the type name (must match the key in DataSourcesMap for mux compat).
func (d *NamespaceV1DataSource) Metadata(
    _ context.Context, req datasource.MetadataRequest, resp *datasource.MetadataResponse,
) {
    resp.TypeName = req.ProviderTypeName + "_namespace_v1"
}

// Configure receives the provider-level Kubernetes client.
func (d *NamespaceV1DataSource) Configure(
    _ context.Context, req datasource.ConfigureRequest, resp *datasource.ConfigureResponse,
) {
    if req.ProviderData == nil {
        return
    }
    d.SDKv2Meta = req.ProviderData.(func() any)
}

// Read calls the Kubernetes API and writes attributes into state.
func (d *NamespaceV1DataSource) Read(
    ctx context.Context, req datasource.ReadRequest, resp *datasource.ReadResponse,
) {
    var state NamespaceV1Model
    resp.Diagnostics.Append(req.Config.Get(ctx, &state)...)
    if resp.Diagnostics.HasError() {
        return
    }

    meta := d.SDKv2Meta().(kubernetes.KubeClientsets)
    conn, err := meta.MainClientset()
    if err != nil {
        resp.Diagnostics.AddError("kubernetes client error", err.Error())
        return
    }

    name := state.Metadata[0].Name.ValueString()
    ns, err := conn.CoreV1().Namespaces().Get(ctx, name, metav1.GetOptions{})
    if err != nil {
        resp.Diagnostics.AddError("error reading Namespace", err.Error())
        return
    }

    state.ID = types.StringValue(ns.Name)
    // … populate state.Metadata, state.Spec from ns.ObjectMeta / ns.Spec …

    resp.Diagnostics.Append(resp.State.Set(ctx, &state)...)
}

Step 5 — Register with the Framework provider

Add the constructor to the DataSources slice in internal/framework/provider/provider.go. Currently that slice is empty (return []func() datasource.DataSource{}) — this is where migrated data sources land.

Framework · internal/framework/provider/provider.go
import "github.com/hashicorp/terraform-provider-kubernetes/internal/framework/provider/corev1"

func (p *KubernetesProvider) DataSources(ctx context.Context) []func() datasource.DataSource {
    return []func() datasource.DataSource{
        corev1.NewNamespaceV1DataSource,
    }
}

Step 6 — Remove from SDKv2 DataSourcesMap (after mux cutover)

During a mux migration, both providers coexist. The Plugin Framework provider takes priority for type names it declares. Once the framework version is stable and tested, remove the entry from DataSourcesMap in kubernetes/provider.go.

Do not remove the SDKv2 entry until the Framework version is fully tested. The mux server (internal/mux/) routes requests to whichever provider claims the type name. Duplicate registrations will cause a startup panic.

8. Common Patterns & Gotchas

Computed vs. Required in data source schemas

In a data source schema, fields that come from the API are Computed: true. Only the fields needed to identify the resource (like metadata.name and metadata.namespace) are Required: true (or Optional). Never mark an API-returned field as Required — that would force the user to supply a value Terraform will immediately overwrite.

SetId in SDKv2

SDKv2 requires you to call d.SetId(someUniqueString) in the Read function. If you forget, Terraform will consider the data source non-existent and return empty values. The Framework equivalent is writing the id attribute into resp.State via the model struct.

The datasource/schema vs. resource/schema import

These are different packages with overlapping type names. A data source uses github.com/hashicorp/terraform-plugin-framework/datasource/schema. Accidentally importing resource/schema compiles but the method signature won't satisfy datasource.DataSource.

No Timeouts needed for most data sources

Timeouts are an advanced pattern only needed if the upstream API call can hang indefinitely. Most Kubernetes Get calls return quickly. Add timeouts only if the data source documentation explicitly mentions them.

Not in config files? Never.

You always declare data sources in .tf files using the data block. There is no other mechanism. They are first-class citizens of HCL configuration — not a workaround, not a special case.
