# kubernetes_manifest_patch

~> **Beta:** This resource is new in the 4.0 beta releases. Its arguments and behavior may still change before version 4.0.0 is released.

Applies fields of an existing Kubernetes object of any kind, built-in or custom, and keeps them set, while the rest of the object stays with whatever created it: a cluster add-on, an operator, another tool or the cluster itself. For example, an environment variable of a DaemonSet that an add-on manages, the tolerations of the cluster's DNS Deployment, a key of a ConfigMap that another tool created, a label of the `default` namespace, or a field of a custom resource.

The manifest names the object and holds only the fields to set. It is sent with [server-side apply](https://kubernetes.io/docs/reference/using-api/server-side-apply/) under the resource's own field manager, as `kubectl apply --server-side --field-manager=<name>` sends a partial manifest, so the cluster records which fields this resource owns. The resource takes the arguments of [`kubernetes_manifest_v2`](manifest_v2.md) and plans the same way, without a request to the cluster. The differences:

| | `kubernetes_manifest_patch` | `kubernetes_manifest_v2` |
|---|---|---|
| The object | Must exist. The patch never creates it. | Is created, and must not exist yet. |
| `terraform destroy` | Gives up the fields, or removes them with `destroy_behavior = "remove_fields"`. The object stays. | Deletes the object. |
| Default field manager | `terraform-patch` | `Terraform` |
| `object` | Not available. The [`kubernetes_resource`](../data-sources/resource.md) data source reads the object. | The object as the cluster returns it. |
| Import | Describes the fields the field manager applied. | Describes the whole object. |

## Example Usage

### Environment variables of an add-on's DaemonSet

```terraform
# Set environment variables of a DaemonSet that a cluster add-on manages.
resource "kubernetes_manifest_patch" "node_agent" {
  manifest = {
    apiVersion = "apps/v1"
    kind       = "DaemonSet"
    metadata = {
      name      = "node-agent"
      namespace = "kube-system"
    }
    spec = {
      template = {
        spec = {
          containers = [{
            name = "agent"
            env = [
              { name = "LOG_LEVEL", value = "debug" },
              { name = "HTTPS_PROXY", value = "http://proxy.example.com:3128" },
            ]
          }]
        }
      }
    }
  }

  # The add-on sets some of these variables itself.
  field_manager {
    force_conflicts = true
  }

  # The nodes run with the new setting when the apply ends.
  wait {
    rollout = true
  }
}
```

Kubernetes merges containers by name and their environment variables by name, so the patch names the container and holds only the variables it sets. The other variables, and the add-on's later changes to them, stay as they are.

### The tolerations of a Deployment, from YAML

```terraform
resource "kubernetes_manifest_patch" "cluster_dns" {
  yaml_body = <<-EOT
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: cluster-dns
      namespace: kube-system
    spec:
      template:
        spec:
          tolerations:
          - key: CriticalAddonsOnly
            operator: Exists
          - key: node-role.kubernetes.io/control-plane
            effect: NoSchedule
          - key: dedicated
            value: system
            effect: NoSchedule
  EOT

  # The add-on owns the list of tolerations.
  field_manager {
    force_conflicts = true
  }
}
```

Some fields are replaced as a whole, such as the `tolerations` and the `nodeSelector` of a pod. The patch then sets the complete list, including the entries the add-on set, and takes it over with `force_conflicts`.

### A key of a ConfigMap and a label of a namespace

```terraform
# A setting in a ConfigMap that another tool created.
resource "kubernetes_manifest_patch" "app_settings" {
  manifest = {
    apiVersion = "v1"
    kind       = "ConfigMap"
    metadata = {
      name      = "app-settings"
      namespace = "apps"
    }
    data = {
      "log.level" = "debug"
    }
  }
}

# A label of a namespace that the cluster created.
resource "kubernetes_manifest_patch" "default_namespace" {
  manifest = {
    apiVersion = "v1"
    kind       = "Namespace"
    metadata = {
      name   = "default"
      labels = { "pod-security.kubernetes.io/enforce" = "baseline" }
    }
  }
}
```

## Schema

### Optional

- `computed_fields` (List of String) Fields of `manifest` that another controller may change after Terraform sets them, for example `spec.replicas` under an autoscaler. Such a change is not reported, and Terraform stops sending a field once another controller owns it. Values the API server defaults or rewrites need no entry here.
- `destroy_behavior` (String) What destroying this resource does with the fields it applied. The object itself is never deleted. `relinquish` (default) leaves the fields at their values and gives up their ownership, so that any client can change them without a conflict. `remove_fields` removes the fields that no other field manager applies, as removing them from the manifest does, also those taken over with `force_conflicts`: Kubernetes keeps no earlier value to restore.
- `field_manager` (Block, Optional) How Kubernetes records the fields this resource owns. (see [below for nested schema](#nestedblock--field_manager))
- `manifest` (Dynamic) The object to patch and the fields to apply to it: an object value with `apiVersion`, `kind` and `metadata.name`, and `metadata.namespace` for an object outside `default`, followed by only the fields this resource sets. Set either `manifest` or `yaml_body`. Write it in HCL or decode YAML with `provider::kubernetes::manifest_decode`. Changing the API group, `kind`, `metadata.name` or `metadata.namespace` moves the patch to another object.
- `show_drift_values` (Boolean) With `yaml_body`: also show the values another client set, in the comment that names the changed fields. The values appear in plan output, so leave this off for objects that hold secrets.
- `timeouts` (Block, Optional) (see [below for nested schema](#nestedblock--timeouts))
- `wait` (Block, Optional) Conditions to wait for after the object is applied. All of them must hold before the apply succeeds. (see [below for nested schema](#nestedblock--wait))
- `yaml_body` (String) The object to patch and the fields to apply to it, as YAML or JSON text holding one object. Set either `yaml_body` or `manifest`. With `yaml_body`, a plan lists the fields another client changed in `drift` and does not show their values.

- `api_version` (String) The API version of the object.
- `drift` (List of String) With `yaml_body`: the fields of the manifest that another client changed or removed since the last apply. A plan that restores them shows this list becoming empty. Always empty with `manifest`, where the plan shows the changed values instead.
- `kind` (String) The kind of the object.
- `name` (String) The name of the object.
- `namespace` (String) The namespace of the object. Empty for a cluster-scoped object, and `default` when the manifest of a namespaced object names none.
- `uid` (String) The UID the cluster assigned to the object.

## What a patch owns

Kubernetes records which client set each field of an object. This resource owns the fields of its manifest, under its field manager name, and nothing else:

- The fields that other clients set are never changed or removed by this resource, also where they share a map or a list with the patched ones, such as the other environment variables of a container. Lists merge as the kind defines: containers, environment variables and ports by their keys, many other lists as a whole.
- A field that another field manager owns with a different value fails the apply with a field ownership conflict that names that manager. `force_conflicts = true` in the `field_manager` block takes the field over. See [Field ownership conflicts](manifest_v2.md#field-ownership-conflicts).
- When another client changes a field of the patch, the next plan restores it, as for `kubernetes_manifest_v2`: with `manifest`, the plan shows the live value changing back; with `yaml_body`, the field is listed in `drift`. Taking a field back from the client that changed it needs `force_conflicts`.
- A field removed from the manifest is removed from the object, unless another field manager also applies it. That includes a field taken over with `force_conflicts`: Kubernetes keeps no earlier value to go back to.
- A null value is left out of the apply, as in `kubernetes_manifest_v2`, and validation warns about it. A field that only this resource applied before is then removed, like any field taken out of the manifest. A field that another field manager set stays as it is: server-side apply cannot remove it, for example an annotation an add-on added.
- `status` and the metadata fields that only the API server sets are ignored. `computed_fields` hands fields over to another controller, as for `kubernetes_manifest_v2`.

A controller that reconciles the object may set a patched field back, for example a managed add-on that applies its configuration again on an update. The next plan shows the change, and applying takes the field back if `force_conflicts` is set. Where an add-on offers a setting in its own configuration, prefer that.

## Field manager names

Each resource that applies fields to one object needs a field manager name of its own: two patches of the object, or a patch and a `kubernetes_manifest_v2`, `kubernetes_labels`, `kubernetes_annotations`, `kubernetes_env` or similar resource of the same object. Server-side apply under one name replaces all the fields applied under that name before, so the resources would remove each other's fields. An apply that would remove fields that this resource's manifest never set fails with "Field manager in use" and names them, and a destroy then leaves all the fields of that name in place, with a warning.

Changing `field_manager.name` moves the fields this resource applied to the new name.

## Objects another Terraform resource manages

A patch is for an object that Terraform does not manage otherwise. When a resource manages the object, set the field there if you can. Where a patch and another resource apply to one object:

- **`kubernetes_manifest_v2`** and a patch apply under their own field manager names and leave each other's fields alone, in whichever order they are applied. A field that both set is a conflict, and after a patch takes it with `force_conflicts`, `kubernetes_manifest_v2` reports it as changed and fails to set it back. Leave the field out of the manifest of `kubernetes_manifest_v2`, or list it in its `computed_fields`: it then sets the field when it creates the object and leaves it to the patch.
- **A resource for the kind**, such as `kubernetes_config_map_v1`, manages each of its arguments in full: its next apply removes a key that a patch added to `data`, and the patch then plans to add it again. Set such values in that resource.
- **A replaced object** does not have the patched fields until the next apply, which the refresh plans. To apply them in the same run as the replacement, replace the patch with the object:

```terraform
resource "kubernetes_manifest_patch" "example" {
  manifest = {
    apiVersion = "v1"
    kind       = "ConfigMap"
    metadata   = { name = kubernetes_manifest_v2.example.name }
    data       = { patched = "1" }
  }

  lifecycle {
    replace_triggered_by = [kubernetes_manifest_v2.example.uid]
  }
}
```

## Destroying a patch

`terraform destroy` never deletes the object. By default, with `destroy_behavior = "relinquish"`, the fields keep their values and lose their owner: the entry of the resource's field manager is removed from the object's field ownership, so that any client, such as the add-on, can set them again without a conflict. If that entry is the only one the object has, it stays, because Kubernetes treats an object without entries as owned in full by a manager named `before-first-apply`.

With `destroy_behavior = "remove_fields"`, the fields that only this resource applies are removed from the object, as removing them from the manifest does. Fields that another field manager also applies stay. A field taken over with `force_conflicts` is removed too, and a list that is replaced as a whole, such as `tolerations`, disappears completely, so use this setting for fields that the patch added. The destroy fails when the object is not valid without a field, such as the image of a container.

A change of `destroy_behavior` takes effect once it is applied. A destroy of an object that no longer exists succeeds.

## The object

The object must exist when the resource is created: make the resource depend on the one that creates the object, through a reference or `depends_on`. A new patch waits up to a minute for an object that a controller creates a moment later, such as the `default` ServiceAccount of a new namespace, and then fails with "Object not found". Every apply sends the UID of the object, so a patch never creates the object again, also if it is deleted during the apply.

When the object is deleted, the refresh removes the resource from the state, and the plan shows it created again: that apply fails until the object exists. When the object is deleted and created again under the same name, the refresh warns about it and the next apply applies the fields to the new object.

Applying and destroying need the `get` and `patch` permissions for the kind. `wait` also uses `watch` when the credentials allow it.

## Limitations

- A patch cannot remove a field that another field manager set, and cannot change `status` or another subresource.
- `metadata.generateName` is not supported.
- The API group, `kind`, `metadata.name` and `metadata.namespace` name the object. Changing one of them replaces the resource: the fields are given up on the old object, or removed with `destroy_behavior = "remove_fields"`, and applied to the new one.
- The values of the manifest appear in plans and in the state, as for `kubernetes_manifest_v2`.

## Import

Import a patch with an ID of the form `apiVersion=<version>,kind=<kind>,[namespace=<namespace>,]name=<name>[,fieldManager=<name>]`. The field manager defaults to `terraform-patch`:

```shell
terraform import kubernetes_manifest_patch.node_agent "apiVersion=apps/v1,kind=DaemonSet,namespace=kube-system,name=node-agent"
```

With Terraform 1.12 or later, an `import` block can use the resource identity instead:

```terraform
import {
  to = kubernetes_manifest_patch.node_agent
  identity = {
    api_version   = "apps/v1"
    kind          = "DaemonSet"
    namespace     = "kube-system"
    name          = "node-agent"
    field_manager = "terraform-patch"
  }
}
```

The imported manifest holds the fields that the field manager applied to the object, so a configuration that sets the same fields plans no change. A field manager that applied nothing yet imports a manifest without fields, and the first apply applies the configured ones.
