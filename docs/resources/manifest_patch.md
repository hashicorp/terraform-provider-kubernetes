# kubernetes_manifest_patch

Owns and reconciles a subset of fields on a **pre-existing** Kubernetes object using Server-Side Apply, without creating or deleting the object. Use it to patch objects owned by Helm, an operator, or a managed add-on (e.g. add an annotation to a Service, set env on the EKS `aws-node` DaemonSet). Destroying the resource relinquishes the fields by default — it does not delete the object. See RFC-012.

`kubernetes_manifest_patch` is the generic form of the single-purpose partial-management resources ([`kubernetes_labels`](labels.md), [`kubernetes_annotations`](annotations.md), [`kubernetes_config_map_v1_data`](config_map_v1_data.md), …): it patches **any field** on **any object** the target already has, using [Server-Side Apply](https://kubernetes.io/docs/reference/using-api/server-side-apply/) field management. It does **not** create or delete the target object.

Use it to modify objects owned by Helm, an operator, or a managed add-on — for example, add an annotation to a Helm-installed Service, set environment variables on the EKS `aws-node` DaemonSet, or set a field a typed resource does not yet expose.

~> **Note** The target object must already exist; `kubernetes_manifest_patch` never creates it. Create it first (for example with [`kubernetes_manifest_yaml`](manifest_yaml.md)) and use `depends_on` if needed.

~> **Note** Set a `patch` leaf to `null` to **remove** that field (Server-Side Apply prunes the fields this resource owns but no longer declares).

~> **Note** Destroying the resource uses `destroy_behavior` — by default `relinquish`, which leaves the object untouched. It never deletes the target object.

### Required

- `kind` (String) Kind of the target object (e.g. "Deployment").

### Optional

- `destroy_behavior` (String) What happens on destroy. `relinquish` (default) leaves the object untouched (the patch is simply forgotten). `remove_fields` removes the fields this resource owns (revert). `remove_fields` requires the SSA `patch` path.
- `field_manager` (String) Server-Side Apply field manager name. Use a unique value so this patch co-owns the object cleanly alongside other managers.
- `force_conflicts` (Boolean) Force apply, taking ownership of patched fields managed by another field manager.
- `ignore_fields` (List of String) Dotted field paths (e.g. "spec.replicas") to exclude from drift detection, so a controller that also writes an owned field (admission mutation, autoscaler) does not cause churn.
- `namespace` (String) metadata.namespace of the target object. Omit for cluster-scoped kinds.
- `patch` (Dynamic, Sensitive) The fields to own, as an object (e.g. `{ spec = { replicas = 3 } }`). Applied with Server-Side Apply, so this resource owns exactly these fields. Setting a leaf to `null` **removes** that field. Exactly one of `patch` or `patch_json` must be set. Marked sensitive because a patch may carry Secret data.
- `patch_json` (String, Sensitive) Escape hatch for operations the `patch` object can't express (RFC-6902 JSON Patch, JSON merge patch, or strategic-merge patch). A JSON string interpreted per `patch_type`. Exactly one of `patch` or `patch_json` must be set. Note: patch_json does not get owned-field drift detection (no SSA ownership).
- `patch_type` (String) Patch strategy. With `patch`: `apply` (default, Server-Side Apply). With `patch_json`: one of `json` (RFC-6902), `merge` (RFC-7386), or `strategic`.

## Example Usage

```terraform
# Set the replica count on a Deployment owned by another tool (e.g. Helm), without
# taking over the whole object. This resource owns only spec.replicas.
resource "kubernetes_manifest_patch" "scale" {
  api_version = "apps/v1"
  kind        = "Deployment"
  name        = "app"
  namespace   = "default"

  patch = {
    spec = {
      replicas = 3
    }
  }
}
```

### Patching a managed add-on and using the JSON escape hatch

```terraform
# Patch an EKS-managed object you do not own: add proxy env to the aws-node DaemonSet,
# and remove an annotation by setting it to null. Destroying this resource relinquishes
# the fields (default) — it never deletes the DaemonSet.
resource "kubernetes_manifest_patch" "aws_node_proxy" {
  api_version = "apps/v1"
  kind        = "DaemonSet"
  name        = "aws-node"
  namespace   = "kube-system"

  field_manager   = "terraform-proxy"
  force_conflicts = true

  patch = {
    spec = {
      template = {
        metadata = {
          annotations = {
            # null removes the field (this manager gives up owning it)
            "eks.amazonaws.com/compute-type" = null
          }
        }
        spec = {
          containers = [
            {
              name = "aws-node"
              env = [
                { name = "HTTP_PROXY", value = "http://proxy.internal:3128" },
                { name = "HTTPS_PROXY", value = "http://proxy.internal:3128" },
              ]
            },
          ]
        }
      }
    }
  }

  destroy_behavior = "relinquish"
}

# Escape hatch: a strategic-merge patch expressed as JSON for cases the object form
# can't express.
resource "kubernetes_manifest_patch" "annotate_service" {
  api_version = "v1"
  kind        = "Service"
  name        = "ingress-nginx-controller"
  namespace   = "ingress-nginx"

  patch_type = "strategic"
  patch_json = jsonencode({
    metadata = {
      annotations = {
        "service.beta.kubernetes.io/do-loadbalancer-hostname" = "example.com"
      }
    }
  })
}
```

## Import

Import an existing patch using a `key=value` identifier that includes the field manager:

```shell
terraform import kubernetes_manifest_patch.example 'apiVersion=apps/v1,kind=Deployment,namespace=default,name=app,fieldManager=terraform-patch'
```

Because `patch` is user configuration and cannot be reconstructed from the live object, add matching configuration after importing.
