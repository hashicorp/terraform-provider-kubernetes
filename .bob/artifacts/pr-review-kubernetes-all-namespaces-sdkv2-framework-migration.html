📝 Five Contract Questions

Does existing configuration change meaning or plan differently?
No. The data source takes no inputs. The only observable outputs are namespaces (a list of strings) and id (a SHA-256 hex string). Both are preserved byte-for-byte. Existing HCL data "kubernetes_all_namespaces" "x" {} is unchanged.
2
Are attributes/types added, removed, renamed, or retyped?
No regression. SDKv2 exposed namespaces (TypeList/Computed/TypeString) and an implicit id. Framework exposes namespaces (ListAttribute{ElementType: types.StringType, Computed: true}) and id (StringAttribute{Computed: true}) explicitly — both correct. No attribute added, removed, renamed, or retyped.
3
Does an existing attribute become required or lose a default?
No. There are no Optional or Required attributes — the schema is entirely Computed. No defaults existed in SDKv2 and none are added in Framework.
4
Does an existing field newly require replacement?
No. Data sources have no replacement semantics. No plan modifiers present.
5
Can the new implementation read existing stored state?
Yes. Schema shape is identical: list-of-strings for namespaces, string for id. No schema version bump; no state upgrader required. The migration test (_MigrateFromSDKv2) mechanically proves this via ExpectEmptyPlan() anchored to a terraform_data resource.

🔴 Blocking Findings

P1
B1 — Framework-only factory in corev1_test.go will break future migrations in this package
internal/framework/provider/corev1/corev1_test.go:31 K8S-MIGRATE-019
Trigger
testAccProtoV6ProviderFactories is providerserver.NewProtocol6WithError(provider.New(...)) — a Framework-only server with no SDKv2 or manifest servers.
Failure
K8S-MIGRATE-019 measured a 6/15 failure rate from this exact pattern. The factory is package-owned and inherited silently by every future PR in corev1. The moment any test in package corev1_test uses an SDKv2-served resource as a fixture (e.g. kubernetes_config_map_v1, kubernetes_namespace_v1 — both Core v1 data sources still on SDKv2) it fails with Invalid resource type — The provider hashicorp/kubernetes does not support resource type and the bug will appear in the follow-on PR, not here.
Impact
The corev1 package is named for Kubernetes Core API v1, which contains dozens of SDKv2 data sources. Every subsequent migration that adds a test using one as a fixture will be broken by this choice.
Correction
Replace the factory with a mux factory that reconstructs all three servers (matching internal/mux/mux.go). The internal/mux package cannot be directly imported (import cycle via kubernetes), so reconstruct inline:
var testAccProtoV6ProviderFactories = map[string]func() (tfprotov6.ProviderServer, error){
    "kubernetes": func() (tfprotov6.ProviderServer, error) {
        ctx := context.Background()
        kubernetesProvider := kubernetes.Provider()
        kubernetesProvider.Configure(ctx, sdkv2.NewResourceConfigRaw(nil))

        upgradedSdk, err := tf5to6server.UpgradeServer(ctx, kubernetesProvider.GRPCProvider)
        if err != nil {
            return nil, err
        }
        upgradedManifest, err := tf5to6server.UpgradeServer(ctx, manifestprovider.Provider())
        if err != nil {
            return nil, err
        }
        return tf6muxserver.NewMuxServer(ctx,
            func() tfprotov6.ProviderServer { return upgradedSdk },
            func() tfprotov6.ProviderServer { return upgradedManifest },
            providerserver.NewProtocol6(provider.New("test", kubernetesProvider.Meta)),
        )
    },
}
Evidence
K8S-MIGRATE-019 measurement table (9/15 PASS Framework-only vs 15/15 PASS mux); internal/mux/mux.go (full server list); admissionregistrationv1_test.go:25 (same defect already exists — this PR is the opportunity to get corev1 right).

B3 — corev1_test.go factory uses eager (init-time) initialization — violates K8S-TESTING-002
internal/framework/provider/corev1/corev1_test.go:22–32 K8S-TESTING-002
Trigger
sdkv2providerMeta() is called at package init time when testAccProtoV6ProviderFactories is initialized as a package-level var. p.Configure(context.Background(), sdkv2.NewResourceConfigRaw(nil)) executes immediately when the test binary is loaded — before a cluster is available, and even when TF_ACC is unset.
Failure
K8S-TESTING-002: "Configure lazily inside the factory, not during package initialization." The test binary panics or errors during init if the SDKv2 provider's Configure path touches the environment unexpectedly. Currently benign, but fragile as the provider grows.
Correction
Wrap initialization inside the factory closure:
var testAccProtoV6ProviderFactories = map[string]func() (tfprotov6.ProviderServer, error){
    "kubernetes": func() (tfprotov6.ProviderServer, error) {
        p := kubernetes.Provider()
        if diags := p.Configure(context.Background(),
            sdkv2.NewResourceConfigRaw(nil)); diags.HasError() {
            return nil, fmt.Errorf("configuring Kubernetes provider: %v", diags)
        }
        return providerserver.NewProtocol6WithError(
            provider.New("test", p.Meta))()
    },
}
Evidence
K8S-TESTING-002 "Correct" block; admissionregistrationv1_test.go:24 (same defect propagated from there).
